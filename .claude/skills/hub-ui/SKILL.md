## Mental model

`generate_hub.py` (2956 lines as of 2026-07) is a one-file static-site generator. Python computes everything up front, then string-builds a single self-contained ~9 MB HTML file. There is no server, no build step, no framework, and no test suite; "the UI" is Python string templates emitting vanilla JS. Leaflet 1.9.4 + leaflet.heat via unpkg CDN are the only external dependencies (map tiles need internet; everything else works offline). Charts are hand-rolled in the embedded JS, not a chart library.

Data flows one way: enriched CSV → Python dicts → `json.dumps` → `const` globals in one `<script>` block → vanilla JS renders the Runs tab and all interactivity client-side. The other tabs arrive as pre-rendered HTML strings.

### How the CSV is read (verified)

`main()` globs `csv_data/*_strava.csv`, takes the lexicographically last (newest date), and calls `load_rows(csv_path)` imported from `lib/generate_dashboards.py`. `generate_hub.py` never calls `csv.field_size_limit` itself; the limit is raised as an **import side effect**, `lib/generate_dashboards.py` executes `csv.field_size_limit(min(sys.maxsize, 2**31 - 1))` at module top (as of 2026-07), and the `from generate_dashboards import ...` at the top of `generate_hub.py` runs it before any CSV is touched. `strava_compile.py` also raises it now (as of 2026-07-08), so all three of `lib/generate_analytics.py`, `lib/generate_dashboards.py`, and `strava_compile.py` set it. Grep: `grep -rn "field_size_limit" .`

## Key files and functions

All in `generate_hub.py` unless noted. Navigate this file by function-name search, never by scrolling: the module-level def cluster sits above the `HUB_CSS` literal, then `HUB_CSS` and `HUB_JS` string literals fill most of the file, then `generate()`/`main()` at the end.

| Tab (bar order) | Generator | Where |
|---|---|---|
| Overview | `overview_html` f-string inside `generate()`, fed by `_overview_stats()`, `_recommendation_html()`, `overview_sections()` (lib/generate_analytics), `render_mileage(weekly_runs(rows))` | generate_hub.py |
| Best Efforts | `body_best_efforts(rows, updated)` | lib/generate_dashboards.py |
| Segments | `body_segments(segments, updated)`; data from `build_segments(runs)` | lib/generate_segments.py |
| Goals | `body_goal_dashboard(rows, updated)` | lib/generate_dashboards.py |
| Analytics | `body_analytics(rows, updated)` | lib/generate_analytics.py |
| Runs | Static shell markup in `generate()` (`#panel-runs`: search/filter pane + detail pane); all content rendered client-side by `HUB_JS` from `const RUNS` | generate_hub.py |

Note the tab-bar button order is Overview, Best Efforts, Segments, Goals, Analytics, Runs (Segments third, as of 2026-07).

Other load-bearing pieces:

- `_build_runs(rows, threshold_mps)`: converts CSV rows to per-run dicts for the JS frontend. Parses the JSON columns `fit_splits` (lap splits), `fit_km_splits`, `fit_gps_polyline`, `fit_distance_stream`; computes `pauses` (`_detect_pauses`) and `pause_ranges` (`_paused_route_ranges`, the polyline index ranges the map draws dotted — JS `pausedRouteRanges` is just a passthrough), `pace_zones`, `best_efforts` (from `BEST_EFFORT_DEFS`), then stamps `run_type` via `_classify_run`. The whole list is embedded as `const RUNS` (~7.2 MB of the HTML as of 2026-07).
- `HUB_CSS = """..."""` and `HUB_JS = r"""..."""`: plain/raw module-level triple-quoted strings, NOT f-strings, so braces inside them need no doubling.
- `generate(...)`: assembles the final HTML string. CSS order is `BEST_EFFORTS_CSS + GOAL_CSS + ANALYTICS_PANEL_CSS + SEGMENTS_CSS + HUB_CSS` in one `<style>` block, hub CSS last so its rules win.
- `main()`: orchestrates and writes `dashboards/TrainingHub.html` (`out.write_text(html, encoding="utf-8")`).

### The emission pattern (real example)

Data is embedded via `json.dumps` and plain concatenation; this is the tail of `generate()` verbatim (as of 2026-07):

```python
"<script>\n"
"const RUNS = " + runs_json + ";\n"
"const SEGMENTS = " + json.dumps(segments, ensure_ascii=False) + ";\n"
"const THRESHOLD_S_KM = " + str(threshold_s_km) + ";\n"
"const HEATMAP_POINTS = " + heatmap_json + ";\n"
+ HUB_JS +
"</script>\n"
```

Three coexisting patterns, by role: plain/raw non-f triple-quoted strings for CSS/JS blocks; f-strings for HTML fragments (e.g. `overview_html`, and per-card markup in the lib modules); explicit `+` concatenation with `json.dumps(..., ensure_ascii=False)` for data embedding. `generate_hub.py` contains zero `{{` (as of 2026-07) because its JS never sits inside an f-string; `lib/generate_analytics.py` does put JS inside f-strings and therefore doubles every literal brace (~45 `{{` occurrences). Grep: `grep -c "{{" lib/generate_analytics.py`.

## Tunables (run classification)

`_classify_run(run, dist_p75, dist_median)` assigns exactly one type, checked in this priority order (as of 2026-07; grep: `grep -n "MISC_MAX_KM" generate_hub.py`):

1. **misc**, `dist_km < MISC_MAX_KM` (1.0 km).
2. **intervals**, `run["is_interval"]` (set by `is_interval(row)` from lib/generate_dashboards).
3. **race**, zone-5 share of zoned time >= `RACE_Z5_SHARE` (0.40). Zone checks 3-5 only run when total zoned time > 0.
4. **threshold**, zone-4 share >= `THRESHOLD_Z4_SHARE` (0.30).
5. **tempo**, zones 3+4 share >= `TEMPO_Z34_SHARE` (0.35).
6. **long**, `dist_km >= LONG_RUN_MIN_KM` (10.0) AND >= the runner's own p75 (`LONG_RUN_PERCENTILE` 0.75) AND >= `LONG_RUN_MIN_RATIO` (1.30) x median.
7. **recovery**, zone-1 share >= `RECOVERY_Z1_SHARE` (0.70).
8. **easy**, fallback (also when there is no threshold, so all zone times are zero).

Zone times come from `_compute_pace_zones(km_splits, threshold_mps)`; the boundaries are a **local literal** `bounds = [0.77, 0.87, 0.93, 1.03]` inside that function, not module constants (grep: `grep -n "bounds = \[0.77" generate_hub.py`). The threshold speed is the best-5K proxy: `_compute_threshold` takes the all-time fastest `best_5k_s`, and `_threshold_at` refines it per run to the fastest 5K within a centered window that widens 60 → 120 → 240 → 480 days (`THRESHOLD_WINDOW_DAYS = 60`), so old runs are judged against contemporaneous fitness. `HUB_JS` mirrors the same boundaries in its zone-colouring code (`if (frac < 0.77) ...` and `ZONE_NAMES`, as of 2026-07), change both together.

## Tunables (pause detection and map overlay)

All in `generate_hub.py` (as of 2026-07; grep: `grep -n "PAUSE_" generate_hub.py`):

| Constant | Value | Meaning |
|---|---|---|
| `PAUSE_MIN_GAP_S` | 20 | absolute floor (s); inter-sample steps shorter than this are never pauses |
| `PAUSE_GAP_MULTIPLIER` | 5 | ... and the step's dt must also be >= this x the run's median step dt |
| `PAUSE_MOVE_MIN_M` | 30.0 | stop→resume separation below which a pause gets no resume coord (lone marker, no dotted hop) |
| `PAUSE_SNAP_WINDOW_M` | 200.0 | half-window (arc metres) searched for the polyline vertex nearest a pause's STOP coordinate |
| `MAP_PACE_WIN_KM` | 0.05 | backward extension of the map's dotted range; must match `PACE_WIN_KM` in `HUB_JS` (the chart's), change both together |

Pause positions on the **chart** come straight from the stream's `d` values; pause ranges on the **map** come from `_paused_route_ranges`, which snaps each pause's STOP GPS coordinate to the polyline (anchored sequentially pause-to-pause) for `i0`, then places the resume end `i1` by stepping `i0`'s arc length forward by `move_m` — the ground actually covered stop→resume, measured along the stream's own coordinates in `_detect_pauses` (`_stream_arc_m`) and stripped from the pause dict before serialisation. Decimation preserves arc length between kept vertices, so this lands on the resume even through a move-during-pause meander where auto-pause froze the recorded distance while the runner wandered on (e.g. Power Pyramid pause 3, ~110 m down King St while recorded distance advances 11 m). Three traps this guards against, from lapped/out-and-back routes: (1) do not reintroduce a global distance-ratio mapping (stream `d`, polyline arc length, and Strava's `Distance` are three different bases, and ground covered while paused advances arc length but not `d`, so ratio error compounds per pause — the pre-2026-07 misalignment); (2) do not use a global-nearest resume snap over a wide window (a superseded `PAUSE_WALK_MPS` walking-budget grabbed a later lap pass); (3) do not match the resume by GPS proximity to the resume coord (a superseded forward `RESUME_RADIUS_M`/`RESUME_MAX_ARC_M` scan, removed 2026-07, grabbed the RETURN-leg pass on an out-and-back meander and overshot up the street — the Power Pyramid pause 3 bug). The `move_m` arc-step handles all three.

## Segment stars round-trip

`build_segments` stamps each segment with a geometric `geo_key` and a `starred` flag read from `cache/segment_stars.json` (a JSON list of geo_keys; the file may not exist until the user creates it). `body_segments` renders each card with `data-geo` and a pre-set `.seg-star` button. In the browser, stars live in localStorage (`strava.segStars`), seeded from the pre-starred cards on first load and authoritative afterwards. Because a `file://` page cannot write to disk, `exportSegStars()` (wired to `#seg-export`) downloads the current set as `segment_stars.json`, which the user manually drops into `cache/` so a full rebuild preserves stars.

## Playbooks

1. **Add a chart or panel to an existing tab.** Compute the data in Python (in `generate_hub.py` for Overview/Runs, or the owning lib module otherwise). Embed it: either interpolate pre-rendered HTML into the tab's body function, or add a `const NEW_DATA = " + json.dumps(...) + ";\n"` line next to `const RUNS` in `generate()` and render it in `HUB_JS`. Add container markup (a `div` with an id) and any CSS to the owning CSS string. Run `python generate_hub.py` (~1.7 s as of 2026-07, no need to re-run the compile stage) and open `dashboards/TrainingHub.html`; check the browser console for errors.
2. **Add a whole new tab.** In `generate()`: add a `<button class="tab" data-panel="X">` to the tab bar and a matching `<div id="panel-X" class="panel" style="...">` block (copy `panel_style` from a sibling). Write a `body_X(rows, updated)`-style generator (new lib module or inline), call it from `main()`, and pass the HTML through `generate()`'s signature like `html_analytics`. Append its CSS to `combined_css` BEFORE `HUB_CSS`. Tab switching is generic, the existing JS keys off `data-panel`/panel ids, so no new wiring is needed unless the tab has interactive JS.
3. **A chart is blank or broken.** Open the browser console first. Usual causes, in order: (a) a JS syntax error from embedded data, check for stray quotes or a literal `</script>` in activity names/descriptions (they are embedded via `json.dumps`, which does not escape `</`); (b) a brace-doubling mistake if the code lives in an f-string (analytics tab especially); (c) missing fields, old runs can lack GPS (`gps_polyline` under 5 points skips all maps), streams, or per-metric values; `availableMetrics(stream)` filters chart tabs to metrics actually present, and all field access null-checks (`!= null`). New JS must degrade the same way, never throw; (d) `None` became `null` where the JS expected a number. Fix in Python, regenerate, hard-refresh.
4. **Change classification thresholds.** Edit the constants above `_classify_run` (or the `bounds` literal in `_compute_pace_zones` plus its JS mirror in `HUB_JS`). Run `python generate_hub.py`. Spot-check the Runs tab: filter chips by type, confirm counts shifted plausibly, and open a few borderline runs (a ~10 km run near the long cutoff, a workout near the tempo/threshold split) to check their badges.

## Pitfalls

- **Never edit `dashboards/TrainingHub.html`.** It is regenerated wholesale on every run and is gitignored; all fixes go in `generate_hub.py` or the lib modules.
- **f-string brace doubling.** `HUB_CSS`/`HUB_JS` are plain/raw strings, so `{` is safe there, but the moment you move CSS/JS into an f-string (as `lib/generate_analytics.py` does) every literal brace must become `{{`. A missed one raises `NameError`/`ValueError` at generation time or silently emits broken JS.
- **`HUB_JS` uses `{s}`/`{z}`-style Leaflet URL templates**, another reason it must stay a non-f string.
- **Navigate by search, not scrolling.** Between `HUB_CSS` and `generate()` the file is almost entirely the `HUB_CSS`/`HUB_JS` string literals; find JS functions with `grep -n "function name" generate_hub.py`.
- **Removing or reordering the `generate_dashboards` import breaks CSV reading** ("field larger than field limit"), because that import is what raises `csv.field_size_limit`.
- **Runs vary in data richness.** GPS-less runs, stream-less runs, and runs missing cadence/calories/HR-derived fields are normal; every renderer guards for them and new code must too (graceful degradation, not hard failure).
- **`json.dumps` does not escape `</script>`.** User-controlled activity names/descriptions are embedded in the script block; treat a mysteriously truncated `<script>` as this until ruled out. UNVERIFIED: no sanitisation for this exists anywhere in the repo (none was found in `generate()` or `_build_runs`).
- **Pace-zone bounds live in two places**: the Python `bounds` literal in `_compute_pace_zones` and the JS mirror in `HUB_JS` (`ZONE_NAMES` block). Changing one without the other desyncs badges from chart colouring.
- **Stars are not in the HTML.** Starring in the browser only touches localStorage; a rebuild only preserves stars that were exported to `cache/segment_stars.json`.
